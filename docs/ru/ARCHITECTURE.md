# Архитектура Rollboard

## Обзор

Rollboard — универсальный движок для настольных игр с движением по маршруту.

- **Бэкенд**: HTTP-сервер на Go с хранением в PostgreSQL
- **Фронтенд**: Svelte 5 + TypeScript + Vite
- **Обмен**: REST JSON API плюс аутентифицированные события комнат по WebSocket

## Устройство бэкенда

```
backend/
├── cmd/server/main.go        — точка входа, флаги, промежуточные обработчики
├── cmd/validate/main.go      — проверка описаний игр без сервера и базы
└── internal/
    ├── game/
    │   ├── definition.go      — типы: GameDefinition, Board, CellDefinition,
    │   │                        EdgeDefinition, ActionDefinition, RuleSet
    │   ├── session.go          — типы: GameSession, GameState, PlayerState,
    │   │                        CellState, PendingAction
    │   ├── engine.go           — исполнение: StartSession, RollDice,
    │   │                        MoveCurrentPlayer, executeActions,
    │   │                        ResolvePendingAction, advanceTurn
    │   ├── resources.go        — единственный путь изменения ресурсов
    │   ├── query.go            — запросы по клеткам
    │   ├── auction.go          — торги по кругу
    │   ├── trade.go            — обмен между двумя игроками
    │   └── validation.go       — ValidateDefinition: геометрия, граф, ресурсы,
    │                             формулы, запросы
    ├── httpapi/                — REST и подъём WebSocket
    ├── identity/               — аккаунты, гости и непрозрачные сессии
    ├── catalog/                — черновики и неизменяемые опубликованные версии
    ├── room/                   — комнаты, участники, модерация и чат

    └── storage/postgres/       — CRUD для игр, сессий и загрузок
```

### Модель движка

Движок **универсален** — в нём нет кода конкретной игры.

**Основные принципы:**

1. **GameDefinition** описывает поле (сетка клеток, направленные рёбра) и
   правила (кубики, ресурсы, типы клеток).
2. **GameSession** создаётся из GameDefinition и списка игроков и хранит
   изменяемое состояние.
3. **Действия** (ActionDefinition) — это данные; они описывают, что происходит,
   когда игрок встаёт на клетку:
   - `gain_resource`, `lose_resource`, `transfer_resource`
   - `set_cell_owner`, `set_cell_level`, `set_cell_mortgaged`
   - `offer_choice` (ветвление по выбору игрока), `random_branch` (ветвление по
     решению сервера)
   - `if_cell_unowned`, `if_cell_owned_by_current`, `if_cell_owned_by_other`,
     `if_cell_level_ge`, `if_cell_mortgaged`, `if_resource_ge`
   - `move_player_to`, `skip_turns`, `reveal_cells`
   - `grant_item`, `remove_item`, `equip_item`, `unequip_slot`, `use_item`
   - `if_has_item`, `if_stat_ge`
   - `if_cells_ge`, `for_each_cell` (вопросы об остальном поле)
   - `start_auction` (торги по кругу)
   - `finish_game`, `eliminate_player`, `log_message`
4. **Предметы** — это каталог того, что игрок носит с собой. Ресурс это число,
   а предмет — названная вещь со своими эффектами; мечом может быть только она.
   Бонусы действуют, лишь пока предмет надет, и никогда не вливаются в
   сохранённый ресурс, поэтому снять экипировку не значит что-то потерять.
   `if_stat_ge` читает эффективное значение, `if_resource_ge` — сырое.
5. **Закрытые клетки** остаются рубашкой вверх, пока на них не встанут или их не
   разведают. Содержимое срезается при сериализации сессии для отправки — и
   только для отправки: в хранилище лежит полное описание, потому что клетка,
   сохранённая в срезанном виде, вернулась бы пустой.

   Ничто из этого не знает про конкретную игру. `set_cell_level` — это дома в
   игре про недвижимость и укрепления в игре про войну; `skip_turns` — это и
   тюрьма, и оглушение.
6. **Ресурсы меняются через один защищённый путь.** Количество — это величина, а
   не направление: вычисленное отрицательное количество отклоняется и попадает в
   лог, а не выполняет действие наоборот. `ResourceRule.Min` и `.Max`
   соблюдаются везде — в действиях, обменах, аукционах, платных рёбрах и бонусе
   за старт, — а перевод передаёт ровно столько, сколько получатель способен
   принять, поэтому платёж в полный карман не уничтожает разницу.
7. **Сервер авторитетен** — кубик бросает сервер, движение считает сервер.
8. Фронтенд отправляет только намерения («хочу бросить»), никогда не результаты.

### Ход сессии

```
StartSession
  → заставка хода (только интерфейс)
  → RollDice → MoveCurrentPlayer → executeActions(OnLand)
    → есть отложенное действие? → ResolvePendingAction → advanceTurn
    → нет? → advanceTurn
  → ход завершён
  → заставка хода следующего игрока
```

### Поток данных

```
Автор правит поле → BoardEditor меняет GameDefinition.board
  → Сохранить → PUT /api/games/:id/draft (JSON)
  → Бэкенд проверяет и кладёт черновик, принадлежащий автору, в PostgreSQL

Автор запускает тестовую игру → POST /api/games/:id/playtest
  → StartSession создаёт GameSession → сохраняется
  → PlaytestPanel рисует живое поле

Игрок жмёт «Бросок» → POST /api/sessions/:id/roll
  → RollDice (генератор на сервере) → MoveCurrentPlayer → действия клетки
  → фронтенд показывает результат, двигает фишку, показывает отложенное действие
```

Сетевые комнаты используют тот же универсальный движок, но клиент отправляет по
WebSocket намерение (`start`, `roll`, `action`, `chat`, `inventory`, `trade`), а
не результат правила. PostgreSQL блокирует и сохраняет снимок комнаты до того,
как хаб опубликует монотонную последовательность. Redis Pub/Sub разносит
принятый снимок, переход или сообщение чата по локальным хабам всех реплик.
Комната ссылается на `game_versions.id`, никогда на изменяемый черновик. Redis
не является авторитетом: PostgreSQL в той же транзакции хранит и сам конверт, и
расписку с UUID клиентской команды. Повтор `start`, `roll`, `action`, `chat`,
`inventory` или `trade` возвращает сохранённый результат, не выполняя команду
второй раз. При переподключении хаб переигрывает до 64 подряд идущих событий
журнала новее `since`; при разрыве или большем диапазоне он безопасно отдаёт
последний снимок из PostgreSQL.

## Запросы по клеткам и аукционы

Сборка полной 40-клеточной «Монополии» очертила границы набора действий, и две
из найденных дыр теперь закрыты. Обе — общие возможности, доступные любому
автору из редактора, а не особенности встроенных шаблонов; примеры разобраны в
**[AUTHORING.md](AUTHORING.md)**.

**Запросы по клеткам.** `CellQuery` выбирает клетки по типу, по полю, которое
придумал автор, и по владельцу (`none`, `current`, `cellOwner`, `other`).
`if_cells_ge` ветвится по количеству совпадений, `for_each_cell` выполняет
список для каждого совпадения, подставляя эту клетку как контекст, а терм
формулы вида `cells` превращает количество в число — именно это позволяет
аренде умножаться на владения. `sameAsCell` сравнивает поле с той клеткой, для
которой идёт вычисление, поэтому «остальная часть этой цветовой группы» —
один запрос, работающий для всех групп, а не по запросу на цвет.

Фильтр владельца намеренно различает гостя и хозяина. Аренда растёт от того, чем
владеет *хозяин* (`cellOwner`), а не тот, кто стоит на клетке, и в словесной
формулировке правила эти двое легко путаются.

**Аукционы.** `start_auction` проводит открытый восходящий аукцион: ставки идут
по кругу, и отложенное действие в каждый момент принадлежит одному участнику.
Форма выбрана потому, что `PendingAction` адресован ровно одному игроку, так что
одновременной закрытой ставке негде жить, — и потому, что торги по кругу делают
аукцион возобновляемым. Он лежит в состоянии сессии, поэтому игрок,
перезагрузившийся посреди торгов, вернётся к ним, а комната, переигрывающая
журнал, переиграет и ставки.

Варианты ставок формирует сервер (несколько повышений и «пас») и принимает
только тот, который сам предложил, перепроверяя баланс в момент ответа.
Победитель платит банку, а список `then` автора выполняется *от имени
победителя*, поэтому «отдать клетку текущему игроку» отдаёт её выигравшему, а не
тому, кто на неё встал.

Действия вкладываются тремя способами — ветвления, телепорт, выполняющий
`onLand` цели, и запрос, выполняющий список для каждой найденной клетки, —
поэтому глубина ограничена 32 уровнями. Описание, зацикленное само на себя,
останавливается событием `action_depth_exceeded`, а не роняет процесс.

## Чего язык действий пока не выражает

- **Нет табличных подстановок.** Ступенчатые значения пишутся нисходящей
  цепочкой `if_*_ge` — работает, но многословно.
- **Нет произвольных ставок.** Аукцион предлагает шаги, сформированные сервером,
  а не число, которое вводит игрок.
- **Платежи упираются в границу, а не проваливаются.** `lose_resource` и
  `transfer_resource` ограничиваются, поэтому описание, которому нужно
  банкротство, должно проверить платёж через `if_resource_ge` и вызвать
  `eliminate_player` в ветке «иначе». Движок не решает это за автора намеренно:
  что считать разорением — вопрос игры, а не среды исполнения.

## Границы реализации

Redis используется только для рассылки между процессами. Авторитет по состоянию
комнат, журналу событий и распискам команд — PostgreSQL. Ограничение частоты
работает в пределах процесса и ключуется адресом клиента, причём заголовкам
прокси верят только от доверенных адресов из настройки. Присутствие
(кто сейчас на связи) не реализовано.

### Граница расширения мини-играми

`launch_minigame` — типизированное зарезервированное действие с неизменяемым
идентификатором модуля и версией. Текущий валидатор его отклоняет, потому что
исполнителя нет. Будущий исполнитель обязан работать вне процесса Rollboard,
получать только явный `MiniGameInvocation`, возвращать результат по схеме и
позволять сервису комнат применять этот результат в своей обычной
авторитетной транзакции. Авторский код мини-игры никогда не должен обращаться к
PostgreSQL или менять сессию напрямую.

## Ключевые правила

- **Геометрия поля**: сетка. `width = столбцы * cellSize`,
  `height = строки * cellSize`. Координаты клеток выровнены по cellSize. Рёбра
  соединяют клетки.
- **Никакого кода конкретной игры**: поведение клеток задаётся данными
  ActionDefinition.
- **Одна система координат**: редактор и игра используют одну геометрию.

## Условия рёбер

У рёбер могут быть условия, определяющие, доступны ли они для прохода.

### Типы условий

| Тип | Поля | Смысл |
|-----|------|-------|
| `always` | — | Всегда доступно (по умолчанию) |
| `dice_total_even` | — | Доступно при чётной сумме кубиков |
| `dice_total_odd` | — | Доступно при нечётной сумме |
| `manual_choice` | `label` | Игрок выбирает путь сам; поднимает отложенное действие `route_choice` |
| `pay_resource` | `resource`, `amount`, `label` | Требует потратить ресурс; поднимает `route_choice` |
| `player_resource_at_least` | `resource`, `amount` | Доступно, только если у игрока есть ≥ N ресурса |

### Как работает выбор маршрута

Когда движение доходит до клетки с несколькими доступными исходящими рёбрами,
у которых стоит `manual_choice` или `pay_resource`:

1. Движение останавливается на текущей клетке.
2. Движок создаёт `PendingAction` с `type: "route_choice"` и списком вариантов.
3. Фронтенд рисует кнопки — по одной на доступное ребро.
4. Игрок нажимает кнопку, фронтенд отправляет выбранный идентификатор ребра.
5. Движок проверяет выбор, списывает ресурс при `pay_resource` и продолжает
   движение.
6. Если ресурса не хватает, возвращается ошибка.

### pay_resource против player_resource_at_least

- `player_resource_at_least` — **пропуск**: ребро доступно, только если ресурса
  достаточно. Проход бесплатен.
- `pay_resource` — **цена**: ребро видно всегда, но выбор списывает ресурс.

### MoveContext

`MoveContext` передаётся в `evaluateCondition()` и содержит:
- `Dice` — броски этого хода
- `Total` — сумма бросков
- `PlayerID` — чей ход (для проверок ресурсов)
- `Step` — номер шага в многошаговом движении

### PendingMovement

Когда `route_choice` прерывает движение на полпути, движок сохраняет
`PendingMovement`:
- `PlayerID` — чьё движение прервано
- `CurrentCellID` — где остановились
- `RemainingSteps` — сколько шагов осталось после выбора
- `Dice`, `Total` — исходный бросок
- `PathSoFar` — уже пройденные клетки

Это позволяет продолжить движение от выбранной клетки на оставшиеся шаги.
