# Translating Rollboard

Rollboard reads its interface text from JSON catalogs on disk at request time.
Adding a language is a file drop and a restart — **no image rebuild, no
recompilation, no code change**.

The image ships English (`en`) and Russian (`ru`).

## Add a language in three steps

### 1. Copy an existing catalog

```bash
cp locales/en.json locales/de.json
```

The file name is the language tag, and it must look like `de`, `pt-BR` or
`zh-Hans`. Anything else is ignored.

### 2. Translate the values

Keys stay in English; only values change.

```json
{
  "app.rooms": "Räume",
  "auth.tab.guest": "Gast"
}
```

Anything you leave out falls back to English, so a partial translation is
usable immediately.

### 3. Restart the application

```bash
docker compose restart app
```

The new language appears in the switcher on its own. Nothing else to do.

## Placeholders

Braces are substituted at render time and must survive translation:

```json
"dashboard.welcome": "Willkommen, {name}. Entwürfe sind privat, bis du eine Version veröffentlichst."
```

A placeholder you drop simply will not appear; one you misspell is printed
literally. The test suite checks that every language uses the same placeholders
as English.

## Plural forms

Languages disagree about how many plural forms they need, so counts are not a
singular/plural pair. Rollboard uses `Intl.PluralRules` and looks up
`<key>.<category>`.

English needs two:

```json
"playtest.playerCount.one": "{count} player",
"playtest.playerCount.other": "{count} players"
```

Russian needs three, because the form depends on the final digits — 1 игрок,
2 игрока, 5 игроков, and 21 игрок again:

```json
"playtest.playerCount.one": "{count} игрок",
"playtest.playerCount.few": "{count} игрока",
"playtest.playerCount.many": "{count} игроков",
"playtest.playerCount.other": "{count} игрока"
```

Use whichever categories your language actually has: `zero`, `one`, `two`,
`few`, `many`, `other`. If you provide none, the bare key is used for every
count, which is correct for languages such as Japanese that do not inflect.

## Error messages

The backend answers with a stable machine code (`ACCOUNT_REQUIRED`,
`ROOM_MEMBERSHIP_REQUIRED`, and so on) alongside its English prose. The
interface shows `errors.<CODE>` from the catalog, and only falls back to the
server's English text when it meets a code it does not recognise. This is why
server messages are translatable at all: translate the `errors.*` keys, not the
server.

## Where the catalogs live

| Context | Location |
|---------|----------|
| Repository | `locales/` |
| Container | `/app/locales` |
| Override | whatever `ROLLBOARD_LOCALES_DIR` points at |

**A mount replaces the directory, it does not merge with it.** If you
bind-mount your own catalogs over `/app/locales`, copy the shipped files in
first or you will lose English and Russian:

```bash
docker run --rm --entrypoint sh ghcr.io/mirivlad/rollboard:latest \
  -c 'tar -c -C /app/locales .' | tar -x -C /srv/rollboard/locales
```

English is additionally compiled into the frontend bundle as a last-resort
fallback, so a missing or misconfigured locale directory degrades to a readable
English interface instead of a page full of raw keys.

## How the language is chosen

1. The language the player last picked, from `localStorage`.
2. Otherwise the best match against `Accept-Language` — `ru-RU` matches a
   catalog published as `ru`.
3. Otherwise English.

## Checking a translation before shipping it

```bash
cd frontend && npm test
```

The suite fails when a language is missing a key that English defines, when it
defines a key English does not, or when its placeholders diverge from the
English ones. Add your language to those assertions in
`frontend/src/lib/i18n.test.ts` if you want it covered too.

## Contributing a translation upstream

Open a pull request adding `locales/<tag>.json`. Nothing else needs to change:
no build configuration, no component edits, no code.
